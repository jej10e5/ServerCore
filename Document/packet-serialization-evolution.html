패킷 조립부 → 직렬화 발전사

71e7a86(패킷조립부 만들기)부터 현재 로컬 작업 트리까지, 커밋 7개를 순서대로 따라가며 “왜 이 코드가 나왔는지”를 정리한 문서입니다. 각 단계는 직전 단계에서 실제로 불편했던 것을 해결하려고 나온 것이라, 순서대로 읽으면 현재 코드가 자연스럽게 이해됩니다.

전체를 한 문장으로

“바이트 배열을 손으로 자르고 붙이던 것”을 → “구조체를 그대로 메모리에 얹는 것”으로 바꿔온 과정입니다.

중간 단계들은 전부 이 방향으로 가는 징검다리입니다. 손계산 오프셋 → 커서(BufferReader/Writer) → 함수로 캡슐화(Make_/Handle_) → 구조체 통짜 매핑(#pragma pack) → 복사 제거(reinterpret_cast) → 가변 리스트 중첩(offset/count).

Stage 0 · 출발점

왜 “조립”이라는 말이 필요한가

TCP는 바이트 스트림입니다. 보낸 쪽이 Send를 3번 나눠 불렀어도 받는 쪽 OnRecv는 한 번에 뭉쳐서 받을 수도 있고, 반대로 한 번에 보낸 걸 잘라서 받을 수도 있습니다. “메시지 경계”라는 개념 자체가 TCP에는 없습니다. (자세한 배경은 TCP 바이트 스트림 참고)

그래서 Stage 1 이전의 Session은 이런 상태였습니다. 

// Stage 1 이전: Session은 "바이트 덩어리"만 넘겨준다
virtual int32 OnRecv(BYTE* buffer, int32 len) override
{
    cout << "OnRecv Len = " << len << endl;   // len이 몇인지 예측 불가
    // ...에코로 그대로 되돌려보내기만 했음
}

에코 서버까지는 이래도 됩니다. 하지만 “로그인 요청”, “이동 요청”처럼 의미 단위가 생기는 순간, 받은 바이트 덩어리를 다시 메시지 단위로 잘라 붙이는 층이 필요해집니다. 이게 패킷 조립부입니다.

Stage 1 · 71e7a86

패킷 조립부 만들기 — PacketSession

문제 — 받은 바이트에서 어디까지가 한 개의 패킷인지 알 수 없다.

해결 — 모든 패킷 맨 앞에 크기(size)를 박아 넣는다. 크기를 알면 자를 수 있다.

이때 등장한 게 PacketHeader 4바이트입니다.

// ServerCore/Session.h
// [size(2)][id(2)][data...][size(2)][id(2)][data...]
struct PacketHeader
{
    uint16 size;    // 헤더를 포함한 이 패킷 전체 크기
    uint16 id;      // 프로토콜 ID (ex. 1=로그인, 2=이동요청)
};

수신 버퍼에 도착한 바이트를 패킷 단위로 잘라내기

size=10id=1data(6B) size=8id=2data(4B) size=20id=3data(3B만 도착…)

파랑·초록은 완성된 패킷이라 즉시 처리합니다. 빨강은 아직 size만큼 안 왔으므로 건드리지 않고 남겨둡니다. 이 “남은 만큼”을 다음 recv 때 이어붙이는 게 RecvBuffer(링버퍼)의 역할입니다. 

// ServerCore/Session.cpp
int32 PacketSession::OnRecv(BYTE* buffer, int32 len)
{
    int32 processLen = 0;
    while (true)
    {
        int32 dataSize = len - processLen;

        // 최소한 헤더는 파싱할 수 있어야 한다
        if (dataSize < sizeof(PacketHeader))
            break;

        PacketHeader header = *(reinterpret_cast<PacketHeader*>(&buffer[processLen]));

        // 헤더에 기록된 패킷 크기를 파싱할 수 있어야 한다
        if (dataSize < header.size)
            break;

        // 패킷 조립 성공
        OnRecvPacket(&buffer[processLen], header.size);

        processLen += header.size;
    }

    return processLen;   // "이만큼 소비했다"를 Session에 알려준다
}

반환하는 processLen이 핵심입니다. len이 아니라 온전한 패킷까지만 소비했다고 보고하면, 남은 조각은 버퍼에 그대로 남아 다음 수신 데이터와 이어집니다.

sealed / abstract 조합

// ServerCore/Session.h
class PacketSession : public Session
{
protected:
    virtual int32 OnRecv(BYTE* buffer, int32 len) sealed;        // 더 이상 재정의 금지
    virtual int32 OnRecvPacket(BYTE* buffer, int32 len) abstract; // 반드시 구현해야 함
};

sealed로 조립 로직을 잠가서 “자르는 건 코어가 책임진다”를 강제하고, abstract로 “해석은 컨텐츠가 한다”를 강제합니다. GameSession·ServerSession은 이제 OnRecvPacket만 구현하면 되고, 들어오는 buffer가 항상 완전한 패킷 하나임을 신뢰할 수 있습니다.

이때의 송신 코드 — 아직 날것

// GameServer/GameServer.cpp
SendBufferRef sendBuffer = GSendBufferManager->Open(4096);
BYTE* buffer = sendBuffer->Buffer();

((PacketHeader*)buffer)->size = (sizeof(sendData) + sizeof(PacketHeader));
((PacketHeader*)buffer)->id   = 1;         // 1 : Hello Msg
::memcpy(&buffer[4], sendData, sizeof(sendData));   // ← 4가 어디서 나온 숫자?
sendBuffer->Close(sizeof(sendData) + sizeof(PacketHeader));

&buffer[4]의 4는 sizeof(PacketHeader)를 사람이 암산한 값입니다. 필드가 하나 늘면 이 숫자를 전부 다시 계산해야 하고, 받는 쪽 숫자도 같이 고쳐야 합니다. 이 불편함이 Stage 2를 부릅니다.

이 단계의 더 자세한 비교는 PacketSession 로컬 변경 분석에 있습니다.

Stage 2 · 258dc01

Buffer Helper — BufferReader / BufferWriter

문제 — 오프셋을 사람이 손으로 계산한다. 필드가 늘면 양쪽을 전부 다시 센다.

해결 — 커서(_pos)를 객체가 들고 있게 한다. 쓰거나 읽을 때마다 알아서 전진.

두 클래스의 뼈대는 동일합니다. 버퍼 + 전체크기 + 현재위치 3개뿐입니다.

// ServerCore/BufferWriter.h
private:
    BYTE*  _buffer = nullptr;
    uint32 _size = 0;   // 버퍼 전체 크기
    uint32 _pos  = 0;   // 지금까지 쓴 위치 = 곧 WriteSize()

// operator<< : 그 자리에 T를 통째로 얹고, 커서를 sizeof(T)만큼 전진
template<typename T>
BufferWriter& BufferWriter::operator<<(T&& src)
{
    using DataType = std::remove_reference_t<T>;
    *reinterpret_cast<DataType*>(&_buffer[_pos]) = std::forward<DataType>(src);
    _pos += sizeof(T);
    return *this;
}

핵심 트릭 — Reserve<T>()

헤더의 size는 다 쓰고 나서야 알 수 있습니다. 그런데 헤더는 맨 앞에 있어야 합니다. 이 모순을 “자리만 먼저 잡아두고 포인터를 들고 있다가 마지막에 채우기”로 풉니다. 

template<typename T>
T* BufferWriter::Reserve()
{
    if (FreeSize() < sizeof(T))
        return nullptr;

    T* ret = reinterpret_cast<T*>(&_buffer[_pos]);
    _pos += sizeof(T);      // 자리는 소비했지만 값은 아직 안 씀
    return ret;             // 나중에 채울 수 있게 포인터를 돌려준다
}

Before — 손계산

((PacketHeader*)buffer)->size = ...;
((PacketHeader*)buffer)->id = 1;
::memcpy(&buffer[4], sendData, ...);

// 받는 쪽
::memcpy(recvBuffer, &buffer[4],
    header.size - sizeof(PacketHeader)
        - 8 - 4 - 2);   // ← 실제 코드

After — 커서가 관리

BufferWriter bw(sendBuffer->Buffer(), 4096);

PacketHeader* header = bw.Reserve<PacketHeader>();
bw << (uint64)1001 << (uint32)100 << (uint16)10;
bw.Write(sendData, sizeof(sendData));

header->size = bw.WriteSize();  // 마지막에 채움
header->id = 1;
sendBuffer->Close(bw.WriteSize());

Before 쪽의 - 8 - 4 - 2를 보세요. uint64 id, uint32 hp, uint16 attack의 바이트 수를 사람이 뺀 겁니다. 필드 하나만 추가돼도 조용히 틀리는 코드입니다. After에서는 br >> id >> hp >> attack이 알아서 커서를 옮기므로 이 뺄셈 자체가 사라집니다.

주의 — 이 시점의 operator>>는 순서 규약일 뿐

BufferWriter가 쓴 순서와 BufferReader가 읽는 순서가 정확히 같아야만 동작합니다. 컴파일러가 검사해주지 않습니다. “쓰는 쪽 3줄, 읽는 쪽 3줄”을 사람이 동기화하는 구조 — 이게 Stage 5의 동기입니다.

이 단계의 더 자세한 비교는 BufferReader / BufferWriter 추가 분석에 있습니다.

Stage 3 · 78d6e9a

패킷 핸들러 생성 — 만드는 곳과 읽는 곳을 짝으로 묶기

문제 — 직렬화 코드가 main()과 GameSession 안에 흩어져 있다. 패킷이 10종류가 되면?

해결 — 패킷마다 Make_XXX(쓰기) / Handle_XXX(읽기) 함수 한 쌍으로 고정.

// GameServer/ServerPacketHandler.h
enum { S_TEST = 1 };

class ServerPacketHandler
{
public:
    static void HandlePacket(BYTE* buffer, int32 len);   // id로 분기하는 라우터
    static SendBufferRef Make_S_TEST(uint64 id, uint32 hp, uint16 attack,
                                     vector<BuffData> buffs);
};

void ServerPacketHandler::HandlePacket(BYTE* buffer, int32 len)
{
    BufferReader br(buffer, len);

    PacketHeader header;
    br.Peek(&header);       // Read와 달리 _pos를 전진시키지 않는다

    switch (header.id)
    {
    default:
        break;
    }
}

Peek이 필요한 이유가 여기서 드러납니다. 라우터는 id만 보고 넘길 뿐, 실제 파싱은 Handle_XXX가 버퍼 처음부터 다시 하기 때문입니다.

변화 ①: OnRecvPacket의 반환형이 int32 → void

71e7a86

virtual int32 OnRecvPacket(BYTE*, int32 len)
{
    // ...
    return len;   // 얼마 썼는지 보고
}

78d6e9a

virtual void OnRecvPacket(BYTE* buffer, int32 len)
{
    ServerPacketHandler::HandlePacket(buffer, len);
}

왜 반환값이 필요 없어졌나? PacketSession::OnRecv가 이미 header.size를 읽어서 processLen += header.size로 전진하고 있기 때문입니다. 즉 “몇 바이트 소비했는지”는 조립부가 이미 아는 정보였고, 컨텐츠에게 물어볼 이유가 없었던 겁니다. sealed/abstract 분리가 여기서 실제 이득으로 나타납니다.

변화 ②: 가변 개수 데이터 — 리스트

고정 필드(id, hp, attack)와 달리 버프 목록은 개수가 매번 다릅니다. 바이트 스트림에는 “여기서 끝”이란 표시가 없으므로, 개수를 먼저 적어두는 방식을 씁니다.

쓰기 (Make_S_TEST)

bw << id << hp << attack;

bw << (uint16)buffs.size();   // 개수 먼저

for (BuffData& buff : buffs)
    bw << buff.buffid << buff.remainTime;

읽기 (Handle_S_TEST)

br >> id >> hp >> attack;

uint16 buffCount;
br >> buffCount;              // 개수 먼저

buffs.resize(buffCount);
for (int32 i = 0; i < buffCount; i++)
    br >> buffs[i].buffid >> buffs[i].remainTime;

변화 ③: BufferWriter::operator<< 오버로드 정리

// 제거됨: const T& 버전
// template<typename T> BufferWriter& operator<<(const T& src);

// 남은 것: 포워딩 레퍼런스 하나로 통합
template<typename T>
BufferWriter& BufferWriter::operator<<(T&& src)
{
    using DataType = std::remove_reference_t<T>;
    *reinterpret_cast<DataType*>(&_buffer[_pos]) = std::forward<DataType>(src);
    _pos += sizeof(T);
    return *this;
}

두 오버로드가 공존하면 bw << buff.buffid(좌변값)에서 어느 쪽을 부를지 모호해집니다. T&&는 템플릿 문맥에서 포워딩 레퍼런스라 좌변값·우변값을 모두 받으므로 하나로 충분합니다. 다만 T가 uint64&처럼 추론될 수 있어 remove_reference_t로 벗겨낸 뒤 캐스팅합니다.

Stage 4 · f77cfdc

인코딩 설정하여 문자열 보내기

문제 — 문자열은 길이가 매번 다르고, 한글은 1바이트가 아니다.

해결 — 길이(글자 수)를 먼저 쓰고, WCHAR(2바이트) 단위로 그대로 복사한다.

서버 — 쓰기

bw << (uint16)name.size();          // 글자 수
bw.Write((void*)name.data(),
         name.size() * sizeof(WCHAR)); // 바이트 수

클라이언트 — 읽기

wstring name;
uint16 nameLen;
br >> nameLen;
name.resize(nameLen);
br.Read((void*)name.data(),
        nameLen * sizeof(WCHAR));

wcout.imbue(std::locale("kor"));
wcout << name << endl;
포인트설명
uint16 길이 접두 널 종료(\0)에 의존하지 않습니다. 문자열 중간에 널이 있어도 안전하고, 읽는 쪽이 정확히 몇 바이트 읽을지 미리 알 수 있습니다.
size() vs * sizeof(WCHAR) 기록하는 건 글자 수, 실제 복사하는 건 바이트 수. L"안녕하세요."는 6글자 = 12바이트입니다. 여기서 *2를 빠뜨리는 게 흔한 실수입니다.
char → WCHAR char sendData[1000] = "Hello World"가 WCHAR sendData[1000] = L"가"로 바뀝니다. 한글은 char 한 칸에 안 들어갑니다.
wcout.imbue(locale("kor")) 패킷이 아니라 콘솔 출력의 문제입니다. 기본 wcout은 비ASCII를 만나면 스트림이 실패 상태로 빠져 아무것도 안 찍힙니다. 로케일을 지정해야 한글이 보입니다.

참고: 문자열 필드는 이후 Stage 5의 #pragma pack 구조체로 넘어가면서 예제에서 잠시 빠집니다. 가변 길이라 고정 크기 구조체에 담기지 않기 때문인데, 이 문제를 offset/count 방식으로 다시 푸는 게 Stage 5~7의 리스트입니다.

Stage 5 · 747a555

패킷 직렬화 — #pragma pack 방식

문제 — 쓰는 쪽 bw << a << b << c와 읽는 쪽 br >> a >> b >> c를 사람이 동기화해야 한다.

해결 — 패킷 모양을 구조체 하나로 선언하고, 바이트 배열을 그 구조체로 통째로 본다.

// DummyClient/ClientPacketHandler.cpp
#pragma pack(1)
struct PKT_S_TEST
{
    struct BuffsListItem
    {
        uint64 buffid;
        float  remainTime;
    };

    uint16 packetSize;   // 공용 헤더
    uint16 packetId;     // 공용 헤더
    uint64 id;
    uint32 hp;
    uint16 attack;

    uint16 buffsOffset;  // 리스트가 시작되는 위치
    uint16 buffsCount;   // 리스트 항목 개수
};
#pragma pack()

왜 #pragma pack(1)이 반드시 필요한가

C++ 컴파일러는 CPU 접근 효율을 위해 구조체 멤버 사이에 패딩을 끼워 넣습니다. 메모리 안에서는 문제없지만, 네트워크로 나가는 바이트 배열에서는 이 패딩이 그대로 “유령 바이트”가 됩니다. 송신·수신 컴파일러 설정이 조금만 달라도 필드가 어긋납니다.

PKT_S_TEST 메모리 배치 — 패딩 있음 vs 없음

기본 정렬에서는 uint64 id가 8의 배수 위치에 놓여야 해서 오프셋 4~7에 패딩 4바이트가 들어가고, 구조체 전체 크기도 8의 배수(32)로 올림되며 꼬리 패딩 6바이트가 붙습니다. 서버가 bw << id << hp << attack으로 빈틈없이 22바이트를 썼는데 클라이언트가 32바이트 구조체로 읽으면 id부터 전부 어긋납니다.

리스트를 offset + count로 표현

Stage 3에서는 “개수 → 항목들” 순으로 흘려 썼습니다. 그런데 구조체 통짜 매핑을 하려면 고정 크기 부분과 가변 크기 부분을 분리해야 합니다. 그래서 고정 부분에는 “리스트가 어디에 몇 개 있다”만 적고, 실제 데이터는 뒤에 붙입니다. 

// GameServer/ServerPacketHandler.cpp
struct ListHeader
{
    uint16 offset;
    uint16 count;
};

ListHeader* buffsHeader = bw.Reserve<ListHeader>();

buffsHeader->offset = bw.WriteSize();   // 리스트가 시작될 위치
buffsHeader->count  = buffs.size();

for (BuffData& buff : buffs)
    bw << buff.buffid << buff.remainTime;

Validate() — 네트워크 입력은 믿을 수 없다

bool Validate()
{
    uint32 size = 0;
    size += sizeof(PKT_S_TEST);
    size += buffsCount * sizeof(BuffsListItem);
    if (size != packetSize)                 // ① 크기 총합이 맞는가
        return false;

    if (buffsOffset + buffsCount * sizeof(BuffsListItem) > packetSize)
        return false;                       // ② 리스트가 패킷 밖으로 나가지 않는가

    return true;
}

구조체를 그대로 얹는 방식의 대가입니다. buffsCount에 65535가 박힌 조작된 패킷이 오면 검증 없이는 그대로 메모리 밖을 읽습니다. “구조체로 보기 전에 반드시 검증”이 규칙이 됩니다.

기준점이 this, 즉 패킷 자신의 시작 주소라는 게 중요합니다. 버퍼 어디에 놓여 있든 상대 위치만 맞으면 동작합니다.

PacketList / PacketIterator — 소유하지 않는 뷰

// DummyClient/ClientPacketHandler.h
template<typename T>
class PacketList
{
public:
    PacketList() : _data(nullptr), _count(0) {}
    PacketList(T* data, uint16 count) : _data(data), _count(count) {}

    T& operator[](uint16 index)
    {
        ASSERT_CRASH(index < _count);   // 범위 밖 접근은 즉시 크래시
        return _data[index];
    }

    uint16 Count() { return _count; }

private:
    T*     _data;    // 버퍼를 가리키기만 한다 (소유 X, 복사 X)
    uint16 _count;
};

vector와 결정적으로 다릅니다. vector는 메모리를 할당하고 복사하지만 PacketList는 수신 버퍼를 가리키기만 합니다. 대신 원본 버퍼가 살아 있는 동안에만 유효하다는 제약이 생깁니다 — 핸들러 안에서만 쓰는 게 원칙입니다.

    return false;

Stage 7 · 현재 로컬 (커밋 전)

중첩 리스트 + 쓰기 전용 빌더

문제 — 버프마다 “영향을 받은 대상 목록(victims)”이 붙는다. 리스트 안의 리스트는 어떻게 담나?

해결 — 같은 offset/count 패턴을 한 단계 더 적용한다. 그래서 offset이 꼭 필요했던 것.

PDL.xml도 같이 자랐습니다.

왜 offset이 없으면 안 되는가

버프가 3개고 각 버프의 victims 개수가 3/1/2로 다릅니다. 즉 버프 항목의 실제 데이터 길이가 제각각입니다. “버프 i의 victims는 어디부터?”를 계산으로 구하려면 앞의 모든 버프를 훑어야 합니다. 각 항목이 자기 데이터 위치를 victimsOffset으로 직접 들고 있으면 한 번에 점프할 수 있습니다. 

struct BuffsListItem
{
    uint64 buffid;
    float  remainTime;

    uint16 victimsOffset;   // 패킷 시작 기준 위치
    uint16 victimsCount;
};

현재 코드가 실제로 만드는 패킷 — 총 118바이트

모든 offset은 패킷 시작(0)을 기준으로 한 절대 위치입니다. PKT_S_TEST 22B + BuffsListItem 16B×3 + victims 8B×(3+1+2) = 118B.

재귀적 Validate()

중첩이 생기면서 검증도 한 단계 깊어집니다. 항목마다 자기 하위 리스트를 검사하고, 누적 크기를 밖으로 넘깁니다.

// BuffsListItem 안
bool Validate(BYTE* packetStart, uint16 packetSize, OUT uint32& size)
{
    if (victimsOffset + victimsCount * sizeof(uint64) > packetSize)
        return false;                       // 내 victims가 패킷 밖으로 안 나가는가

    size += victimsCount * sizeof(uint64);  // 누적 크기에 더한다
    return true;
}

// PKT_S_TEST 안
bool Validate()
{
    uint32 size = 0;
    size += sizeof(PKT_S_TEST);
    if (packetSize < size)
        return false;

    if (buffsOffset + buffsCount * sizeof(BuffsListItem) > packetSize)
        return false;

    // buffs 자체 크기 추가
    size += buffsCount * sizeof(BuffsListItem);

    BuffsList buffList = GetBuffsList();
    for (int32 i = 0; i < buffList.Count(); i++)
    {
        if (buffList[i].Validate((BYTE*)this, packetSize, OUT size) == false)
            return false;
    }

    // 최종 크기 비교
    if (size != packetSize)
        return false;

    return true;
}

마지막 size != packetSize가 강력합니다. 모든 조각의 합이 정확히 패킷 크기와 같아야 통과하므로, 빈틈이나 겹침이 있는 조작된 패킷은 걸러집니다. 위 118바이트 예제라면 22 → 70 → 94 → 102 → 118로 누적되어 packetSize와 일치합니다.

참고로 Validate()가 자기 아래 정의된 BuffsList/GetBuffsList()를 쓸 수 있는 건, 클래스 안 멤버 함수 본문은 클래스 전체가 완성된 뒤에 해석되기 때문입니다(complete-class context).

쓰는 쪽도 구조체 방식으로 — PKT_S_TEST_WRITE

이제 읽는 쪽만 구조체를 쓰고 쓰는 쪽은 bw << a << b인 비대칭이 남았습니다. 게다가 중첩 리스트는 offset을 나중에 채워야 해서 흘려쓰기로는 표현이 어렵습니다. 그래서 Make_S_TEST가 통째로 삭제되고 빌더 객체가 들어왔습니다. 

// GameServer/ServerPacketHandler.h
struct PKT_S_TEST_WRITE
{
    PKT_S_TEST_WRITE(uint64 id, uint32 hp, uint16 attack)
    {
        _sendBuffer = GSendBufferManager->Open(4096);
        _bw = BufferWriter(_sendBuffer->Buffer(), _sendBuffer->AllocSize());

        _pkt = _bw.Reserve<PKT_S_TEST>();     // 고정부 자리 예약
        _pkt->packetSize = 0;    // To Fill
        _pkt->packetId = S_TEST;
        _pkt->id = id;
        _pkt->hp = hp;
        _pkt->attack = attack;
        _pkt->buffsOffset = 0;   // To Fill
        _pkt->buffsCount = 0;    // To Fill
    }

    BuffsList ReserveBuffsList(uint16 buffCount)
    {
        BuffsListItem* first = _bw.Reserve<BuffsListItem>(buffCount);
        _pkt->buffsOffset = (uint64)first - (uint64)_pkt;   // 포인터 차이로 offset 계산
        _pkt->buffsCount  = buffCount;
        return BuffsList(first, buffCount);
    }

    BuffsVictimsList ReserveBuffsVictimsList(BuffsListItem* buffsItem, uint16 victimsCount)
    {
        uint64* first = _bw.Reserve<uint64>(victimsCount);
        buffsItem->victimsOffset = (uint64)first - (uint64)_pkt;
        buffsItem->victimsCount  = victimsCount;
        return BuffsVictimsList(first, victimsCount);
    }

    SendBufferRef CloseAndReturn()
    {
        _pkt->packetSize = _bw.WriteSize();   // 마지막에 확정
        _sendBuffer->Close(_bw.WriteSize());
        return _sendBuffer;
    }

private:
    PKT_S_TEST*   _pkt = nullptr;
    SendBufferRef _sendBuffer;
    BufferWriter  _bw;
};

이제 GameServer.cpp의 호출부가 “패킷을 조립한다”기보다 “객체를 채운다”에 가까워집니다.

PacketList가 쓰기에도 그대로 재사용된다는 점이 깔끔합니다. buffList[0] = { 100, 1.5f }는 operator[]가 참조를 돌려주므로 SendBuffer 메모리에 직접 쓰는 것입니다. 중간 vector가 없습니다.

이를 위해 바뀐 BufferWriter::Reserve

Before — 1개만

template<typename T>
T* BufferWriter::Reserve()
{
    if (FreeSize() < sizeof(T))
        return nullptr;

    T* ret = reinterpret_cast<T*>(&_buffer[_pos]);
    _pos += sizeof(T);
    return ret;
}

After — N개 연속

template<typename T>
T* BufferWriter::Reserve(uint16 count)   // 기본값 1
{
    if (FreeSize() < (sizeof(T) * count))
        return nullptr;

    T* ret = reinterpret_cast<T*>(&_buffer[_pos]);
    _pos += (sizeof(T) * count);
    return ret;
}

배열 예약이 가능해지면서 “리스트 자리를 통째로 잡고 → 나중에 채운다”가 성립합니다. 기본 인자 count = 1 덕분에 기존 Reserve<PKT_S_TEST>() 호출은 그대로 동작합니다.

미묘한 개선 — offset의 기준점이 바뀌었다

시점코드기준
747a555buffsHeader->offset = bw.WriteSize();버퍼 시작
현재_pkt->buffsOffset = (uint64)first - (uint64)_pkt;패킷 시작

지금은 패킷이 buffer[0]에서 시작하므로 두 값이 같습니다. 하지만 읽는 쪽은 data = (BYTE*)this; data += buffsOffset; 즉 패킷 기준으로 해석합니다. 새 방식은 읽는 쪽 해석과 기준이 정확히 일치하므로, 나중에 한 버퍼에 패킷을 이어 붙이거나 오프셋을 두는 위치가 바뀌어도 깨지지 않습니다.

지금 상태에서 알아둘 점

① 서버 쪽 PacketList의 begin()/end()가 아직 깨진 버전

PacketIterator/PacketList가 ClientPacketHandler.h와 ServerPacketHandler.h에 그대로 복사되어 두 벌 존재합니다. 클라이언트 쪽은 현재 로컬 작업에서 고쳤지만, 서버 쪽은 아직 깨진 상태입니다.

GameServer/ServerPacketHandler.h:44 — 현재 (깨진 상태)

PacketIterator<T, PacketList<T>> begin() { return PacketIterator<T, PacketList, T >> (*this, 0); }
PacketIterator<T, PacketList<T>> end()   { return PacketIterator<T, PacketList, T >> (*this, count); }

DummyClient/ClientPacketHandler.h:49 — 로컬에서 수정된 버전

PacketIterator<T, PacketList<T>> begin() { return PacketIterator<T, PacketList<T>>(*this, 0); }
PacketIterator<T, PacketList<T>> end()   { return PacketIterator<T, PacketList<T>>(*this, _count); }

두 군데가 틀렸습니다. 템플릿 인자가 PacketList<T>가 아니라 PacketList, T >>로 들어가 있고, count는 선언된 적 없는 이름입니다 (멤버는 _count).

그런데 왜 지금 빌드가 되나? 클래스 템플릿의 멤버 함수는 실제로 호출될 때만 인스턴스화되기 때문입니다. 서버 코드는 buffList[0] = {...}처럼 인덱스로만 접근하고 ranged-for를 쓰지 않아서 begin()/end()가 한 번도 인스턴스화되지 않습니다. 실제로 Server.sln을 Debug/x64로 빌드하면 세 프로젝트 모두 성공합니다. 서버에서 for (auto& b : buffList)를 쓰는 순간 비로소 컴파일 에러가 납니다.

커밋 기록도 같은 이야기를 합니다. 62b9d7a는 이 깨진 begin()/end()를 그대로 커밋했는데, 당시 클라이언트도 for (int32 i = 0; ...) 인덱스 순회를 쓰고 있었습니다. ranged-for 사용과 수정이 둘 다 현재 로컬 작업에서 처음 등장합니다 — 쓰는 순간 드러난 것입니다.

② #pragma pack(1) 범위가 PKT_S_TEST_WRITE까지 덮고 있음

// GameServer/ServerPacketHandler.h
#pragma pack(1)
struct PKT_S_TEST { ... };          // ← 얘는 패킹이 필요함 (와이어 포맷)

struct PKT_S_TEST_WRITE
{
    PKT_S_TEST*   _pkt;
    SendBufferRef _sendBuffer;      // shared_ptr — 네트워크로 나가지 않는 객체
    BufferWriter  _bw;
};
#pragma pack()                       // ← 여기서 닫힘 (line 138)

PKT_S_TEST_WRITE는 와이어 포맷이 아니라 헬퍼 객체입니다. 네트워크로 나가지 않으므로 패킹할 이유가 없고, shared_ptr 같은 객체를 1바이트 정렬로 두는 건 정렬 이점을 잃는 것 외에 좋을 게 없습니다. #pragma pack()을 PKT_S_TEST 닫는 }; 바로 뒤(현재 84~85행 사이)로 올리는 게 의도에 맞습니다. 참고로 클라이언트 쪽(ClientPacketHandler.cpp)은 이미 PKT_S_TEST만 감싸고 있습니다.

③ 자잘한 잔재

  • ClientPacketHandler.cpp의 Handle_S_TEST 첫 줄 BufferReader br(buffer, len);은 이제 아무 데서도 쓰이지 않습니다 (제자리 캐스팅으로 전환하면서 남은 것).
  • BuffsListItem::Validate의 BYTE* packetStart 매개변수도 함수 본문에서 쓰이지 않습니다. 하위 리스트가 더 깊어질 때를 대비한 자리로 보입니다.
  • ServerPacketHandler.h의 PKT_S_TEST에는 Validate()가 없습니다. 서버는 이 패킷을 만들기만 하고 읽지 않으므로 지금은 문제없지만, 양방향이 되면 검증 로직도 두 벌 관리 대상이 됩니다.
